Traditional event management applications often struggle with concurrency races during high-demand registration windows, silent venue conflicts, untracked schedule shifts, and AI chatbots that hallucinate outdated schedules. Quantum Net solves these challenges through:

  • Atomic Ticket Generation & Capacity Locking: Prevents overselling by locking available seats atomically in database transactions, issuing structured cryptographic pass identifiers (QN-2026-XXXX).
  • Automated Waitlist Queue Promotion: Automatically shifts overflowing participants onto a FIFO priority waitlist and promotes the next eligible candidate instantaneously if a seat is vacated.
  • Transactional Anomaly Engine: Handles sudden event cancellations, cascading payment refunds, venue scheduling overlaps, and unauthorized capacity modifications.
  • Live Cloud PostgreSQL Integration: Seamlessly connected to serverless PostgreSQL (Neon) using Prisma ORM with connection pooling, migrations, and schema sync.
  • AURA-NET Global AI Chatbot: A context-aware AI telemetry assistant operating across all 12 frontend interfaces, strictly grounded in live database queries to eliminate hallucinations.

4. Anomaly Engine & Critical Business Logic

The heart of Quantum Net's operational reliability is the Cosmic Anomaly Engine (src/services/anomaly.service.js). It enforces strict physical and operational constraints:

1. Venue Conflict Detection

Before any new event or venue alteration is committed, the engine evaluates existing bookings sharing the target venue. Times are parsed into minutes from midnight (00:00 to 23:59). An overlap is mathematically identified if: 

(Start_Time_A < End_Time_B) && (End_Time_A > Start_Time_B) on same Date && same Venue

Conflicting deployments are rejected with HTTP 409 Conflict, preventing double-booked auditoriums.

2. Atomic Capacity & Waitlist Queue Handling

When a registration is received, the engine computes confirmed seats inside a transaction. If confirmed bookings equal or exceed total capacity:

  • The registration status is set to WAITLISTED.
  • No pass ticket code is issued (held in queue).
  • The participant receives a confirmation of their priority queue placement.

3. Participant Deregistration & Instant Seat Promotion

When a confirmed participant cancels their registration, the engine atomically vacates the seat, selects the earliest waitlisted participant (ORDER BY registrationDate ASC), promotes their status to CONFIRMED, generates a unique ticket ID (QN-2026-XXXX), and dispatches a notification alert.

4. Transactional Event Cancellation & Cascading Refunds

When an administrator cancels an event, the engine performs a synchronized transaction:

  • Marks the Event status as CANCELLED.
  • Marks all confirmed registrations as CANCELLED with cancellation timestamps.
  • Updates all associated Payment records to REFUND_PENDING with refund dates.
  • Broadcasts individual alert notifications to every affected participant.
  • Appends immutable records to EventHistory and AuditLog.

A. Conversational Grounding Architecture

Aura-Net prevents hallucinations by querying the real PostgreSQL database before formulating answers: 

User Query (Frontend) → POST /api/ai-chat → Auth & Context Resolution → Real DB Retrieval
→ Grounded Telemetry Context → Gemini Generative AI / Deterministic Fallback → Verified Natural Answer

B. Role-Based Privacy Enforcement

  • Unauthenticated Guests: Cannot view personal ticket passes or private user registrations. The bot politely guides them to sign in.
  • Authenticated Participants: Can retrieve and inspect strictly their own registered passes, ticket IDs, and seat details. Accessing another user's pass is blocked.
  • Administrators: Granted clearance to request aggregated system telemetry, participant counts, total revenue, and capacity breakdowns. Normal users asking for admin stats are rejected.

Aura-Net preserves conversational session history in sessionStorage and sends the last 6 exchanges with every request. Pronouns such as "Where is it happening?" or "Has it changed?" are automatically resolved to the event currently in context.

6. Security, Authentication & Verification

  • Cryptographic Password Hashing: Passwords hashed using bcrypt with salt rounds of 10.
  • Stateless JWT Authentication: Tokens signed with HMAC-SHA256 and verified per request.
  • Zero Frontend Credential Exposure: Database connection strings (DATABASE_URL), JWT secrets, and AI keys (GEMINI_API_KEY) exist strictly in server-side environment variables.
  • Automated Test Verification: The project includes an end-to-end test suite (tests/quantum-net.test.js) verifying 30 distinct invariant scenarios including transaction rollback resilience, capacity boundary conditions, waitlist promotions, and AI privacy guards.
